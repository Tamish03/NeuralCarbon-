01 · Product Concept

The Product Idea

Not a dashboard. An autonomous carbon decision-intelligence engine that sits between sensor data and operational decisions.

NeuralCarbon
Autonomous Industrial Carbon Intelligence Platform

NeuralCarbon is a production AI system where your trained LightGBM/XGBoost ensemble becomes the decision brain of an industrial operations platform. It doesn't just predict CO₂ — it prescribes optimal operational changes, simulates regulatory policy impacts, detects emission anomalies in real-time, and closes a feedback loop that makes the model smarter with every deployment cycle.

The system operates in three intelligence modes: Predict (what will emissions be?), Prescribe (what should we change?), and Protect (what risk is approaching?). Each mode is powered by a different component of your existing pipeline — MAPIE for prediction intervals, DiCE for prescription, ADWIN for protection.

⚙️ Industrial Operations 🌍 Environmental Compliance 📈 ESG Reporting ⚖️ Carbon Credit Markets 🏛️ Regulatory Policy Simulation 💰 Cost-Emission Optimization

FastAPI Endpoint Design
# POST /predict — core prediction + conformal interval # Returns: { co2_kg, lower_bound, upper_bound, cluster_id, risk_level } # POST /explain — async SHAP + LIME for one prediction # Returns: { shap_values[], lime_weights[], top_feature, direction } # POST /prescribe — DiCE counterfactuals (what must change?) # Returns: { scenarios[{changes, predicted_reduction, feasibility}] } # GET /drift/status — ADWIN detector health # Returns: { drift_detected, last_alarm_at, severity, recommendation } # POST /simulate/policy — regulation scenario engine # Input: { emission_limit_kg, time_horizon_hours } # Returns: { compliance_rate, required_at_reduction, cost_impact } # POST /feedback — operator labels a prediction (active learning) # Input: { prediction_id, actual_co2_kg, operator_notes } # Queues record for next retraining cycle # WS /stream — real-time prediction feed via WebSocket
Database Schema (TimescaleDB — time-series optimized)
-- Predictions table (hypertable, partitioned by time) CREATE TABLE predictions ( id UUID PRIMARY KEY, ts TIMESTAMPTZ NOT NULL, -- indexed automatically at_val FLOAT, v_val FLOAT, ap_val FLOAT, rh_val FLOAT, co2_pred FLOAT, co2_lower FLOAT, co2_upper FLOAT, -- conformal interval cluster_id INT, risk_level TEXT, shap_top_feature TEXT, shap_direction TEXT ); -- Drift events log CREATE TABLE drift_events ( id UUID, ts TIMESTAMPTZ, feature TEXT, drift_score FLOAT, severity TEXT, auto_retrain_triggered BOOLEAN ); -- Feedback queue (active learning) CREATE TABLE feedback_labels ( prediction_id UUID, actual_co2 FLOAT, operator_note TEXT, label_quality FLOAT, used_in_retrain BOOLEAN DEFAULT false );
03 · Advanced Features

14 Features That Stand Out

Every single feature maps directly to code already in your notebook. This is integration, not invention.

🔮
Counterfactual Prescription Engine
Operator inputs current readings. System runs DiCE to generate 3 ranked scenarios: "Reduce AT by 4°C → saves 18% CO₂. Increase V by 8 cmHg → saves 12%." Each scenario shows operational feasibility score.
dice-ml → /prescribe endpoint
⚠️
Real-Time Emission Risk Scorer
Every prediction is tagged LOW / MODERATE / HIGH / CRITICAL based on (a) predicted value vs regulatory limit, (b) conformal interval width (model uncertainty), and (c) distance from the nearest high-emission cluster centroid.
MAPIE + KMeans → risk_level field
🏛️
Policy Simulation Engine
Regulator sets a new CO₂ limit. System simulates: "At this limit, X% of your historical readings would violate. Required AT reduction: 6.2°C. Estimated compliance cost: calculated from operational changes." No other student project has this.
Your XGB model → scenario sweeps
🧠
Interactive SHAP Explorer
Every prediction renders an interactive SHAP waterfall chart. User can hover over each feature bar to see: "AT contributed +142 kg/h because it was 31°C, 3.2σ above average." Served via async endpoint, cached in Redis.
shap.TreeExplainer → Redis cache
📡
ADWIN Concept Drift Monitor
Background worker streams prediction residuals through your ADWIN detector. When drift detected: (1) dashboard alert fires, (2) drift event logged to DB, (3) if severity HIGH, auto-queues retraining job. Includes seasonal drift calendar.
river.drift.ADWIN → background worker
🌿
Model Carbon Ledger
CodeCarbon wraps every inference batch. The UI shows a live "Model Carbon Account": total CO₂ emitted by the AI system itself, per-day trend, and a comparison: "This week your model emitted 0.003g — equivalent to charging a phone 0.01%." Honest sustainability.
CodeCarbon → /metrics endpoint
🔁
Operator Feedback Loop
After each prediction, operator can enter the actual CO₂ reading. The system computes label quality score (how wrong was the model), stores it in feedback_labels table, and when 200+ high-quality labels accumulate, auto-triggers retraining pipeline.
PostgreSQL → active learning queue
🎯
Cluster Operational Mode Detector
Every input is classified into one of your 4 operational clusters (Cold/Mild/Warm/Hot mode) via the saved KMeans model. The prediction screen shows: "You are in Hot/Peak mode — expect +18% higher CO₂ than baseline. Top driver: AT."
kmeans_k4.pkl → cluster context
📊
Pareto Trade-off Advisor
Business dashboard shows the Pareto frontier from your multi-objective Optuna run: "Current model accuracy costs 0.004g CO₂/inference. You can reduce to 0.001g with only 2% RMSE loss — recommend switching to the green model." Automated decision support.
Optuna Pareto → decision API
⏱️
Time-Series Forecast Mode
Batch mode accepts 24 future hours of AT/V/AP/RH forecasts (from weather API), runs predictions for all, and returns: hourly CO₂ forecast, peak emission window, recommended operational schedule to stay under limit.
LightGBM batch → schedule optimizer
📋
ESG Auto-Report Generator
Monthly PDF report auto-generated: total CO₂, worst day, best day, compliance rate, model accuracy, drift events, counterfactual savings achieved. Ready to submit to ESG compliance officers or carbon auditors. No manual work.
ReportLab/WeasyPrint → PDF API
🔍
LIME vs SHAP Agreement Score
For each prediction, the system computes how much LIME and SHAP agree on the top features. High disagreement = "This prediction has uncertain explanation — treat with caution." A meta-XAI validation layer no other portfolio has.
SHAP + LIME cosine similarity score
🌡️
Weather API Auto-Fill
User enters their plant location. System calls OpenWeatherMap, auto-populates AT, RH, AP from live weather data. User only needs to enter V (vacuum — plant-specific). Reduces input friction to one field. Feels like a real product.
OpenWeatherMap API → auto-feature fill
📈
Evidently Data Quality Gate
Before any batch job runs, Evidently compares the incoming data distribution against your training distribution. If >20% feature drift detected, batch is blocked with report: "Input data drifted significantly — predictions may be unreliable."
evidently → pre-batch quality gate

08 · Wow Factor

3 Features That Make Interviewers Stop

These are the features where the interviewer puts down their pen and says "wait, can you explain that again?"

01
🔮 The Prescriber
Autonomous Counterfactual Prescription

When a prediction comes back HIGH risk, the system automatically asks DiCE: "Generate 3 operationally feasible scenarios to reduce this below the limit." These are ranked by feasibility score and presented as an actionable decision card — not a chart, not a number, but a recommendation you can hand to a plant manager.

The key insight: every other XAI project explains why the model predicted X. Yours also explains what to do about it. That's the difference between explainability and intelligence.

Interviewer line: "So your model doesn't just predict — it prescribes?"
02
🧾 The Carbon Ledger
AI That Audits Its Own Environmental Cost

CodeCarbon wraps every inference batch. The system maintains a running "Model Carbon Account": total CO₂ emitted by the AI system itself (not the power plant — the model), per-day trend, and a sustainability rating of the model vs alternatives from the Pareto run.

This creates a recursive argument: a system that predicts CO₂ and also measures its own CO₂. The system can say: "This week your plant emitted 12,400 kg of CO₂. To predict that, I emitted 0.0003g." That kind of self-aware sustainability narrative is entirely unique in any ML portfolio.

Interviewer line: "The model tracks its own carbon footprint?"
03
🏛️ The Policy Engine
Regulatory Compliance Simulator

A compliance officer types: "What if the EU Carbon Border Adjustment Mechanism sets a 300 kg/h limit next year?" Your system sweeps your historical data, returns: "72% compliance rate. Gap of 84 kg/h on average in peak summer. Required AT reduction: 5.8°C. Estimated carbon credit deficit: 2,400 units."

This is policy simulation — a feature that governments and consultancies build with teams of analysts. You built it with your regression model and a parameter sweep. That reframing — from ML model to policy tool — is what makes an interviewer see a product, not a project.

Interviewer line: "This is basically what McKinsey charges for."

Interview Script — What to Say
Q: "Tell me about your most advanced project."
"I built NeuralCarbon — an autonomous carbon decision-intelligence platform. The ML model isn't just a predictor, it's the brain of a multi-layer system. At the core is a LightGBM ensemble with monotone physics constraints — temperature must always increase predicted emissions, vacuum must decrease them. Around that I built conformal prediction intervals that give mathematically guaranteed 90% coverage, a DiCE counterfactual engine that answers 'what must change to reduce emissions by 20%', and an ADWIN drift detector that triggers retraining when the model starts degrading in production. The whole thing is containerized with Docker, deployed on Render and Vercel, with a GitHub Actions CI/CD pipeline that runs model regression tests on every push."
Q: "What's unique about the explainability?"
"Most XAI projects just show a SHAP bar chart and call it done. I run both SHAP and LIME on every prediction and compute an agreement score between them — features where they disagree get flagged as 'uncertain explanation, treat with caution.' I also built a policy simulation layer where a compliance officer can type in any emission limit and the system sweeps the full historical dataset to return compliance rate, required operational changes, and carbon credit impact. That's the difference between explaining a prediction and making a decision."
Q: "How is this different from a student project?"
"Three things. First, active learning feedback loop — operators submit actual readings after predictions, those labels queue to PostgreSQL, and when 200+ accumulate the system auto-triggers retraining. Second, the model audits its own environmental cost — CodeCarbon wraps every inference batch and the UI shows a 'Model Carbon Ledger', because a system predicting CO₂ should measure its own CO₂. Third, concept drift is handled operationally — not just detected, but responded to: drift severity HIGH auto-queues a retrain job. These aren't features you add. They're the features that make a system production-ready."
